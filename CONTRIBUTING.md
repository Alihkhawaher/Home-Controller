# Contributing to Home Controller

Thank you for helping. Home Controller grows one device family at a time, and every bug report, connector request,
test on a real device and pull request makes it better for everyone.

By taking part you agree to follow the [code of conduct](CODE_OF_CONDUCT.md).

## Ways to help

- **Report a bug.** Use the [bug report form](https://github.com/Alihkhawaher/Home-Controller/issues/new?template=bug_report.yml).
- **Ask for a device.** Use the [connector request form](https://github.com/Alihkhawaher/Home-Controller/issues/new?template=connector_request.yml).
  The most useful thing you can tell us is whether the device has a local API.
- **Test on your devices.** Confirming that a model works, or describing exactly how it fails, is valuable.
- **Write a connector.** Follow [docs/writing-a-connector.md](docs/writing-a-connector.md).
- **Improve the app or the docs.** For anything larger than a small fix, open an issue first so we can agree on the
  approach before you spend time on it.

Security problems are reported privately, never in a public issue. See [SECURITY.md](SECURITY.md).

## Development setup

You need:

- **JDK 17**
- **Android SDK** with platform 34 (Android Studio installs it)
- Git

```sh
git clone https://github.com/Alihkhawaher/Home-Controller.git
cd Home-Controller
./gradlew test assembleDebug
```

On Windows use `gradlew.bat`. If Gradle cannot find the SDK, set `ANDROID_HOME` or add `sdk.dir=/path/to/sdk` to
`local.properties` (it is git-ignored). Install on a connected phone with `./gradlew installDebug`.

No hardware? Debug builds include a **Simulated devices** connector: two air conditioners and a dimmable lamp that
live in memory, so you can work on the UI and automations on an emulator.

Continuous integration runs `./gradlew test assembleDebug` on every push and pull request to `main`. Run it locally
before you push.

## Project layout

| Path | Contents |
|---|---|
| `core/` | The plugin contract and the automations engine. Pure Kotlin, no Android. |
| `connectors/<id>/` | One device family per module. Pure Kotlin, no Android. |
| `app/` | The Android app: UI, hub service, storage. |
| `docs/` | Architecture, the connector guide, protocol notes. |
| `branding/` | Icon and store graphics, generated by `branding/build.py`. |
| `fastlane/` | Store listing text and images (F-Droid and Google Play format). |

## Code guidelines

- **Kotlin official code style** (`kotlin.code.style=official`), lines up to 120 characters.
- **Keep logic out of Android.** Anything that decides what happens (parsing, mapping, automation rules) belongs in
  `core` or a connector, where it runs as a JVM unit test.
- **Test what you change.** New behaviour in `core` or a connector comes with unit tests. Connectors are tested
  against a fake transport, never a real device on someone's network.
- **Suspend, do not block.** Network and disk I/O run in `suspend` functions on `Dispatchers.IO`.
- **Write for the user.** Error messages say what happened and what to do next, in plain words.
- **Document the public API.** A short KDoc on every public class and function in `core` and in connectors.
- **No new heavy dependencies** without discussing them in an issue first.

## The connector rules

Every connector follows the rules in [docs/writing-a-connector.md](docs/writing-a-connector.md#the-rules). In short:
local network only; never log or expose a key, token or password; `read()` never changes a device; validate every
change before sending anything.

## Keep private data out of the repository

This is a public repository. Never commit:

- real IP addresses, MAC addresses, serial numbers or Wi-Fi names. In code, tests and docs use the documentation
  range `192.0.2.0/24` and made-up MACs;
- device keys, tokens, passwords or captured traffic that contains them;
- signing keystores or `keystore.properties` (both are git-ignored).

When you share captured packets or logs in an issue, replace those values first.

## Commits and pull requests

- Keep a pull request to one topic. Smaller pull requests are reviewed faster.
- Write commit subjects in the imperative, under about 70 characters: `Add Shelly connector`,
  `Fix fan speed after mode change`.
- Fill in the pull request template, including the checklist.
- Add a line to `CHANGELOG.md` under the unreleased version for anything a user would notice.
- Update the docs when behaviour changes: the README's devices table, `docs/connectors/<id>.md`, or
  `docs/architecture.md`.

## Branding

The icon and the store graphics are generated from code. To change them, edit the geometry or the pages in
`branding/` and run `python branding/build.py --render`. See [branding/README.md](branding/README.md).
